# `opencode/space-bunny-free`는 어떤 모델과 비슷한가?

## 결론부터

**이 데이터만으로는 특정 모델의 이름을 말할 수 없다.**

이번 측정에서 `opencode/space-bunny-free`는 보정 후 **92.5%**의 정확도를 기록했다. 결함 문항 두 개를 제외하면 **94.7%**다. 그러나 이 결과만으로 `GPT-5`, Claude, Gemini 또는 다른 특정 모델과 동급이라고 결론 내릴 수는 없다.

이유는 간단하다.

1. 실제로 측정한 프런티어 상용 모델이 없다.
2. 비교한 앵커 모델과의 차이가 측정 오차 범위 안에 있다.
3. 벤치마크 점수는 모델만이 아니라 하네스, 추론 예산, 도구 접근 방식의 영향을 크게 받는다.
4. 표본이 작고, 측정 과정에서 하네스와 문항의 결함도 발견됐다.

따라서 이 연구가 지지하는 가장 강한 결론은 다음뿐이다.

> **`opencode/space-bunny-free`는 이번 하네스와 문항 세트에서 높은 점수를 냈다. 하지만 현재 데이터로는 어떤 특정 프런티어 모델과 닮았는지 식별할 수 없다.**

이 문서는 그 결론에 이르는 과정과 한계를 설명한다. 핵심 결과만 보고 싶다면 [§6](#6-최종-판정)으로 가면 된다.

## 1. 무엇을 측정했나

측정 대상은 `opencode/space-bunny-free`다.

- 문항: 88개
- 반복: 문항당 2회
- 총 실행: 176회
- 실행 방식: `opencode run`을 실제로 호출
- 의존성: Node.js 내장 모듈만 사용
- 원본 로그: [`reports/round1/`](reports/round1/)

이 연구는 모델의 자기평가를 받아 적은 것이 아니라, 모델을 실제로 실행한 뒤 답을 별도의 규칙으로 채점했다.

### 숫자의 출처를 구분해야 한다

이 저장소의 숫자는 다음 네 종류로 구분한다.

| 태그 | 의미 |
|---|---|
| `measured` | 이 환경에서 직접 실행해 얻은 값. 원본 로그가 있다. |
| `reported` | 다른 기관이나 사람이 공개한 값을 가져온 것. 직접 재현하지 않았다. |
| `derived` | measured 또는 reported 값을 계산해 얻은 값. |
| `assumed` | 분석에 필요한 가정. |

중요한 사실은 이것이다.

> **실제 프런티어 플래그십 모델은 이 환경에서 하나도 측정하지 못했다.**

GPT-5 계열, Claude Opus, Gemini Pro, Grok 등은 프로바이더 오류나 쿼터 문제로 실행되지 않았다. 따라서 프런티어 모델 점수는 모두 외부 공개 자료를 읽어온 `reported` 값이다. 직접 측정한 비교 모델인 GLM, Muse, Kimi도 프런티어 플래그십이 아니라 접근 가능한 앵커다.

## 2. 측정 결과

하네스가 처음 보고한 정확도는 86.9%였지만, 원본 로그를 다시 감사하는 과정에서 하네스와 스코어러의 결함이 발견됐다.

| 기준 | 결과 | 의미 |
|---|---:|---|
| `raw` | **86.93%** | 하네스의 최초 판정. 실패 실행도 오답으로 포함 |
| `conservative` | **92.53%** | 측정 실패를 제외하고 스코어러 결함을 보정. 결함 문항은 오답으로 유지 |
| `full` | **94.71%** | 위 보정에 더해 답이 존재하지 않는 문항 2개를 제외 |

가장 보수적으로 인용할 값은 **92.5%**다. 94.7%는 결함 문항 두 개를 제외한 분석용 값이다. 세 값 모두 이 저장소에서 직접 얻은 `measured` 값이다.

### 범주별 결과

심사 후, 결함 문항을 제외한 `full` 기준이다.

| 범주 | 정확도 |
|---|---:|
| reasoning | 30/30 (100%) |
| function calling | 16/16 (100%) |
| long context | 14/14 (100%) |
| format control | 12/12 (100%) |
| robustness | 12/12 (100%) |
| abstention / hallucination | 12/12 (100%) |
| instruction following | 27/28 (96.43%) |
| multilingual | 25/30 (83.33%) |
| code | 13/16 (81.25%) |

이 표로 범주별 우열을 주장해서는 안 된다. 범주별 문항 수가 작아 신뢰구간이 넓다. 예를 들어 100%와 81%의 차이가 있어도 이 표본만으로 “reasoning 능력이 code 능력보다 우수하다”고 말할 수 없다.

## 3. 실제 앵커와 비교하면

같은 문항 세트의 공유 부분집합에서 접근 가능한 모델도 측정했다. 앵커에도 subject와 같은 심사 규칙을 적용했다.

| 모델 | 심사 후 정확도 |
|---|---:|
| `opencode/space-bunny-free` | 94.71% |
| `nvidia/z-ai/glm-5.3-flash` | 90.70% |
| `meta/muse-spark-1.3` | 97.67% |
| `nvidia/moonshotai/kimi-k3` | 94.74% |

겉으로 보면 subject가 GLM보다 높고 Muse보다 낮다. 하지만 공유된 43문항에서 반복 측정과 쌍대응 검정을 적용하면:

- GLM 대비 차이: **+4.65%p**, exact McNemar p = 1.000
- Muse 대비 차이: **−2.33%p**, exact McNemar p = 0.250
- 측정된 재현성 기준: 약 **7.37%p**

두 차이 모두 측정 오차 범위 안이다. 따라서 다음과 같이 말해야 한다.

> **subject가 GLM보다 높거나 Muse보다 낮다는 점수 차이는 관찰됐지만, 이 표본으로는 실제 능력 차이라고 판정할 수 없다.**

Kimi의 61.9% 원시 점수는 능력보다 전송 실패의 영향을 크게 받았다. 여러 실행에서 답변 본문이 전달되지 않았기 때문에 능력 비교에 사용하지 않았다.

## 4. 왜 프런티어 모델과 직접 비교할 수 없나

에이전틱 벤치마크의 점수는 모델 하나의 고정된 속성이 아니다. 다음 요소가 함께 점수를 만든다.

> **모델 × 스캐폴드 × 추론 예산 × 도구 접근 × 채점 방식**

같은 모델과 같은 벤치마크도 하네스나 사고 모드만 바꾸면 큰 폭으로 달라진다. 이 저장소에서 수집한 공개 자료에는 구성에 따라 약 **−4.37%p부터 +43.64%p**까지 차이가 난 사례가 있다.

따라서 subject의 점수와 외부 리더보드 점수를 단순히 나란히 놓고 “이 모델과 같다”고 말하는 것은 정당화되지 않는다. subject가 사용한 서비스의 내부 추론 예산도 공개되지 않았다.

프런티어 표와의 비교에서 말할 수 있는 것은 제한적이다.

> **subject의 성능은 공개된 2025–2026 프런티어 모델 점수의 중상위 범위와 양립한다. 하지만 그 범위 안에서 어떤 모델을 특정하거나 배제할 수는 없다.**

“가장 가까운 모델” 순위를 제시하지 않은 것도 같은 이유다. 후보마다 비교 가능한 축 수가 다르고, 축별 오차 범위가 겹친다. 그런 순위는 실제 유사도보다 데이터가 있는 축의 수를 반영한다.

## 5. 무엇이 잘못됐고, 어떻게 보정했나

감사 과정에서 다음 문제들이 확인됐다.

### 하네스 문제

- 긴 프롬프트 하나가 Linux의 `argv` 길이 제한을 넘어 모델을 호출하지 못했다.
- 실패 레코드에도 스코어가 적용돼 전송 실패가 오답으로 중복 집계됐다.
- 문서에는 전송 실패를 정확도 분모에서 제외한다고 적혀 있었지만, 실제 코드가 그 계약을 지키지 않았다.

### 스코어러 문제

- 기권 답변에 날짜나 숫자가 포함되면 정답인 기권도 오답으로 처리하는 정규식이 있었다.
- 숫자 스코어러가 다단계 답변의 첫 숫자를 잘못 읽는 사례가 있었다.
- 이 때문에 총 8개의 판정이 모델의 행동이 아니라 스코어러 결함 때문에 바뀌었다.

### 문항 문제

- `fmt-nested-02`: 프롬프트는 구분자 없는 `S240`을 요구하지만 기대 답은 `S-240`이었다.
- `fmt-flat-01`: 주어진 정보만으로는 정답을 결정할 수 없는 문항이었다.

두 문항은 모든 모델에서 제외했다. 모델에 유리하게 임의로 정답 처리하지 않은 이유는, 그 문항이 실제로 시험한 능력을 알 수 없기 때문이다.

### 도구 사용 문제

`--pure`는 주변 워크스페이스의 지시와 주입을 차단하지만, 모델이 스스로 도구를 호출하는 것까지 막지는 않는다. 5회 실행에서 `bash` 호출이 발생했고 모두 정답 처리됐다. 따라서 이 측정은 완전히 “도구 없는 모델” 측정이라고도 할 수 없다.

이 문제들을 발견했다고 해서 결과가 자동으로 신뢰할 만해지는 것은 아니다. 다만 원본 로그를 보존하고, 원래 판정과 수정 판정을 분리해 기록했기 때문에 어떤 숫자가 왜 바뀌었는지는 추적할 수 있다.

## 6. 최종 판정

### 말할 수 있는 것

- `opencode/space-bunny-free`는 이 문항 세트와 이 하네스에서 보정 후 **92.5%**, 결함 문항 제외 시 **94.7%**를 기록했다.
- 접근 가능한 실측 앵커인 GLM, Muse와의 차이는 이번 표본에서 통계적으로 구분되지 않았다.
- 서비스 호출 자체는 가능했지만, end-to-end 시간의 대부분은 모델 생성이 아니라 CLI 시작과 프로바이더 대기였다.
- 하네스, 스코어러, 문항의 결함이 결과에 영향을 줄 수 있다는 사실을 확인했고, 그 영향을 별도로 기록했다.

### 말할 수 없는 것

- `space-bunny-free`가 GPT-5, Claude, Gemini, Grok 중 무엇과 같은지
- 특정 모델보다 확실히 우수하거나 열등한지
- 이 결과를 다른 스캐폴드나 다른 추론 예산에 일반화할 수 있는지
- end-to-end 레이턴스를 모델 자체의 속도로 해석하는 것

### 한 문장 요약

> **이 연구는 `space-bunny-free`의 이번 측정 점수는 보여주지만, 그것이 어떤 프런티어 모델인지 식별해 주지는 않는다. 현재 가장 정직한 결론은 “높은 점수를 냈지만 모델 정체는 판별 불가”다.**

## 7. 라운드 2: 세 솔버와 제3자 판정자

라운드 2는 다른 질문을 다룬다. 겉으로는 하나의 모델처럼 보이지만 내부적으로는 세 솔버 인스턴스인 시스템을, 다른 모델 계열의 패널이 채점했다.

결과는 다음과 같다.

- 제3자 판정 결과: **89.66%**
- 최고 단일 인스턴스: **88.51%**
- 차이: **+1.1%p**, 통계적으로 유의하지 않음
- 순진한 다수결: **75.86%**, p = 0.0034

다수결이 낮아진 이유는 합의가 틀려서가 아니라, 세 인스턴스의 의견이 갈릴 때 **기권**했기 때문이다. 이 문항에서는 기권을 오답으로 처리했다. 기권하지 않고 무작위로 하나를 고르는 방식도 89.66%에 도달했다.

따라서 라운드 2의 결론은 다음이다.

> **이 과업에서는 제3자 판정자가 무작위 선택보다 추가 정확도를 제공하지 않았다.**

자세한 결과는 [`ROUND2.md`](ROUND2.md)에 있다.

## 8. 레이턴스와 비용

subject의 end-to-end 중앙값은 24,817ms였지만, 순수 모델 구간은 496ms였다. 전체 시간의 약 93%가 프로세스 시작과 프로바이더 대기였다.

그러므로 이 측정에서 “subject가 다른 모델보다 몇 배 빠르다”고 말하면 안 된다. 여기의 end-to-end 레이턴스는 모델 레이턴스가 아니라 CLI와 서비스 대기 시간을 포함한 값이다. 또한 `opencode run`은 토큰 델타를 제공하지 않으므로 진짜 TTFT도 측정하지 못했다.

subject는 free tier로 실행됐기 때문에 비용은 0이다. 이는 효율성이 아니라 과금되지 않았다는 뜻이다. 토큰 수는 별도 기록했지만, 일부 출력은 `chars/4` 추정치이므로 실제 비용 계산에 그대로 사용할 수 없다.

## 9. 재현하기

요구 사항은 Node.js v20 이상이다. 오프라인 검증은 다음 한 줄로 실행한다.

```bash
./scripts/verify.sh
```

이 명령은 모델을 호출하지 않고 테스트, 문항 재생성, 통계 self-test를 수행한다.

실제 측정을 다시 하려면 다음 명령을 사용한다.

```bash
cd harness
node bin/run-bench.mjs --items items.json \
  --models opencode/space-bunny-free \
  --reps 2 --concurrency 1 --out ../reports/round1/subject-88
```

분석 재생성:

```bash
node harness/adjudicate.mjs --strict
node harness/adjudicate-anchors.mjs --strict
node harness/stat-verify.mjs
node harness/psycho-verify.mjs
node harness/matching.mjs
```

실행 원본과 감사 결과는 `reports/`에 보존돼 있다. 문항, 통계, 출처에 대한 자세한 설명은 다음 문서를 참고한다.

- [`METHODOLOGY.md`](METHODOLOGY.md): 측정 설계
- [`FINDINGS.md`](FINDINGS.md): 결과 요약
- [`LIMITATIONS.md`](LIMITATIONS.md): 한계와 타당성 위협
- [`ROUND2.md`](ROUND2.md): 라운드 2 결과
- [`data/ATTRIBUTION.md`](data/ATTRIBUTION.md): 외부 자료와 저작 표시
